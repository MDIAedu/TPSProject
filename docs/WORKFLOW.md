# Workflow

## 목적

이 문서는 AI 에이전트가 task를 진행할 때 따라야 할 작업 순서, 진행 제약, 상태 관리 규칙을 정의합니다.

## 적용 범위

- 이 문서의 `작업 흐름`은 이미 생성된 task 문서를 기준으로 해당 task를 처음 구현 시작할 때만 적용합니다.
- 새 task 문서를 생성하거나 초안을 작성할 때는 이 문서의 `작업 흐름`을 적용하지 않습니다.
- 같은 task를 한 번 진행한 뒤, 이후 멀티턴으로 수정 사항을 반영할 때는 전체 `작업 흐름`을 반복하지 않고, 작업 흐름의 1, 4, 8~10과 12~14의 확인·기록 단계를 기준으로 진행합니다. 
- 이미 `완료`된 task에 수정 요청이 오면 해당 단계 상태를 `진행중`으로 되돌리고, 결과 확인이 끝나면 다시 `완료`로 갱신합니다.
- 다만 새 파일 생성, 구조 변경, 에디터 자산 작업, 또는 최초 합의 범위를 넘는 변경이 생기면 6, 7을 다시 진행하고, 구현 후에는 11의 의심 정리도 함께 진행합니다.

## 문서 우선순위

문서 해석 우선순위는 아래와 같습니다.

1. 사용자 직접 요청
2. 현재 진행 중인 task 문서
3. `docs/WORKFLOW.md`
4. `docs/PLANS.md`
5. 나머지 프로젝트 문서

`docs/HARNESS.md`는 규칙 운영 절차를 다루는 메타 문서라 위 우선순위의 경쟁 대상이 아니며, 규칙 추가·조정·이탈 대응은 항상 HARNESS.md의 절차를 따릅니다.

아래 `진행 제약`은 task 문서를 포함한 어떤 문서도 덮어쓰지 못합니다. 사용자 직접 요청은 범위와 승인 제약을 조정할 수 있지만, 비밀값의 출력·기록 금지는 어떤 경우에도 변하지 않습니다.

문서끼리 충돌하거나 현재 저장소 상태와 맞지 않으면, 구현 전에 불일치를 먼저 보고하고 수정 범위를 제안합니다.

## 작업 흐름

이미 생성된 task 문서를 기준으로 해당 task를 처음 구현 시작할 때, 아래 순서로 작업합니다.
아래 순서는 형식적으로 진행하지 않으며, 각 단계를 건너뛰지 않고 실제로 수행합니다.

1. 관련 task와 선행 산출물을 확인합니다.
2. `docs/PLANS.md`에서 현재 단계 상태를 확인하고 작업 시작 시 `진행중`으로 갱신합니다.
3. `docs/ARCHITECTURE.md`의 내용을 모른다면 확인합니다.
4. 관련 코드와 현재 맵, Blueprint, 자산 구조를 읽습니다. 관련 코드가 아직 없으면 이 단계는 건너뜁니다.
5. `docs/STYLEGUIDE.md`의 내용을 모른다면 확인합니다.
   - 특히 구현 방식과 승인 요청 작성 전에 `Unreal Editor 작업 규칙`을 기준으로 판단해야 한다.
6. 아래 항목들을 보수적으로 판단하며, 하나라도 해당되거나 조금이라도 의심되면 `책임 범위 의심 파일`에 기재합니다. 기재는 분리가 필요하다는 판단과는 별개입니다.
    - 같은 성격의 내용이 여러 파일에 반복되는지
    - 공통화 가능성이 조금이라도 있는지
    - 추가할 코드의 성격이 대상 파일의 현재 책임 범위와 다른지
    
7. 구현 전 반드시 아래 `구현 진행 승인 요청` 섹션의 형식으로 승인 요청을 출력하고, 사용자 승인을 받은 뒤 다음 단계로 넘어갑니다.
8. 필요한 코드 변경을 구현합니다.
9. `docs/TESTING.md`의 현재 실행 확인 모드에 따라 확인을 진행합니다.
10. 구현 후 `docs/TASK_WRITING.md`의 작성 규칙에 맞춰 task 문서를 실제 코드 기준으로 갱신합니다.
11. 구현 전 승인 요청의 `책임 범위 의심 파일`은 구현 후 상태에 따라 `Pending Issues 관리` 규칙에 맞게 정리합니다.
12. 사용자에게 필요한 수동 작업 또는 결과 확인을 요청합니다.
13. 결과 확인이 끝나면 아래 `작업 로그 관리` 규칙에 따라 로그를 정리합니다.
14. 확인이 완료된 뒤 task 문서와 `docs/PLANS.md`에서 현재 단계 상태를 `완료`로 갱신합니다.

## 구현 진행 승인 요청

구현 전 승인 요청은 반드시 아래 형식으로 출력합니다.

**[구현 진행 승인 요청]**
- 생성 후보 파일:
- 변경 후보 파일:
- 변경 요약:
- 에디터 자산 필요 여부: 있음(어떤 자산인지) / 없음
- 책임 범위 의심 파일: (조금이라도 의심되면 기재, 분리 여부는 사용자가 결정, 의심이 전혀 없으면 "없음")
- 의심 사유: (없으면 "없음")
- 의심에 대한 제안 : (의심 파일마다 분리안과 기존 파일 유지안을 각각 설명하고 사용자가 선택하게 한다. 이 항목 작성이 의심 해소를 뜻하지 않는다.)
- 의심에 대한 추천 진행 : (분리안/유지안, 간단한 이유)
- 사용자 승인 전 구현 안 함

## 진행 제약

- 구현은 task 구현 항목에 명시된 것만 합니다. 범위 밖 항목은 구현하지 않습니다.
- 범위 밖 작업이 필요해지면(새 폴더, 새 플러그인, 새 모듈, 대규모 리팩터링, 대규모 에셋 구조 변경 등) 이유와 범위를 사용자에게 알리고 승인을 받은 뒤 진행합니다.
- 프로젝트 내 민감한 계정 정보, API 키, 인증 토큰, 비밀값은 기본적으로 읽지 않습니다. 사용자가 명시적으로 요청한 경우에만 필요 최소한으로 접근하되, 어떤 경우에도 출력하거나 코드·문서·로그·커밋에 적지 않습니다.
- 결과 확인이 끝나기 전에는 다음 단계로 넘어가지 않습니다.
- 구현과 문서 갱신은 같은 작업 흐름 안에서 함께 반영합니다.

## 상태 관리 원칙
- 최근 작업 로그에는 구현, 실행 확인, 결과 확인 결과를 남깁니다.
- `docs/PLANS.md`, `docs/LOGS.md`, `docs/PENDING_ISSUES.md` 같은 기록 문서의 운영 규칙은 이 문서를 기준으로 관리합니다.
- 정상 진행이 막히면 상태를 바꾸지 않고, 막힌 이유를 사용자에게 보고합니다.

## Pending Issues 관리
- 해소되지 않은 의심은 `docs/PENDING_ISSUES.md`에 기록합니다.
- 이번 작업에서 기존 구조를 유지하기로 했더라도, 그 결정이 의심 해소를 뜻하지 않으면 `해소되지 않은 의심`으로 보고 `docs/PENDING_ISSUES.md`에 기록합니다.
- 같은 파일과 같은 성격의 의심은 중복으로 추가하지 않습니다.
- 실제로 해소된 항목은 `docs/PENDING_ISSUES.md`에서 제거합니다.

## 작업 로그 관리

- `docs/PLANS.md`의 `최근 작업 로그`는 최신 진행 상황 확인용으로 유지합니다.
- `docs/PLANS.md`의 `최근 작업 로그`가 20줄 이상이 되면, 작업 중인 에이전트는 가장 오래된 15줄을 `docs/LOGS.md`로 이동하고 최신 5줄만 남깁니다.
- 이동한 로그는 삭제하지 않고 `docs/LOGS.md`에 유지합니다.
